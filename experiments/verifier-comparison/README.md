# Rails ソースと Lean の対応検査を比べる

同じ在庫確保サービスに対し、Ruby から Lean を決定論的に生成する方式と、独立に書いた Lean に Ruby の意味が一致するかを決定論的に検査する方式を比べる。両方の担当者には同じ固定ソースと CLI の契約を渡した。各担当者のコンテキストを分け、相手の実装とこの比較用の変更は渡さなかった。PR のコミットを固定し、両方の CLI を同じ Ruby 4.0.9 と Lean 4.36.0 の GitHub Actions ランナーで起動する。 [元のサービス](https://github.com/s4na/keisiki/blob/1b67c63b8406715bfe4112b2a5ae8d4ef1200575/example/app/services/reserve_stock.rb) · [生成案 #24](https://github.com/s4na/keisiki/pull/24) · [独立案 #25](https://github.com/s4na/keisiki/pull/25)

## 比べ方

同じソースを９通りで渡し、終了コード、標準出力・標準エラー、経過時間を保存する。初期在庫２、数量１、同一 ID の再送という前提で、人が Ruby の編集を確認して分類する。元の版が検証できることを実験成立の条件とする。

| 分類 | 判定で見ること |
| --- | --- |
| 意味を変えない変更 | コメント追加と、条件値を明示的な分岐で返す書き換えで再承認が必要か |
| P1 の違反 | 初回または再送で誤って減算する条件を含め、予約結果・数量の誤りが証明済みとして通過しないか |
| 前提の変化 | トランザクションを外した版、動的ディスパッチへ置き換えた版を保証できるか。対応外のため止めたケースは証明による検出と区別する |

終了コード 0 は各方式が宣言した範囲での検証成功、1 は対応や性質の不成立、2 は診断に基づいて未対応と実行エラーに分ける。サービス全体を実行した結果は、Rails と実 PostgreSQL を使った統合検証が別に扱う。CIの計測時間は１ケース１回の値で、方式の開発工数や長期の保守工数は計測対象外とする。 [統合検証 #23](https://github.com/s4na/keisiki/pull/23)

生成案の初回CIでは、正常版の証明と出力の再現に成功し、反例を探す Lean コードでリストの列挙がコンパイルに失敗した。初回版の判定を保存したうえで、候補の列挙だけを修正した版も同じ入力で実行する。初回版と修正版の結果を追えるよう、それぞれのコミットを固定する。 [反例の列挙を修正したコミット](https://github.com/s4na/keisiki/commit/e2104124d0e0e0dad5a6e888b6698db614fa3ec9)

## 実測と採用方針

| 入力の分類 | 生成案の初回版 | 生成案の修正版 | 独立 Lean の照合案 |
| --- | --- | --- | --- |
| 元のソース・コメント追加（２件） | ２件検証 | ２件検証 | ２件検証 |
| 同値な分岐への書き換え（１件） | 未対応 | 未対応 | 未対応 |
| P1 に反する変更（４件） | 実行エラー３件、未対応１件 | Lean が確認した反例３件、未対応１件 | 命令の不一致１件、未対応３件 |
| トランザクション除去・動的ディスパッチ（２件） | ２件未対応 | ２件未対応 | ２件未対応 |

検証成功として通った不具合は０件だった。予約作成時の数量違いは全方式で対象外となり、反例や意味の不一致の判定には到達しなかった。独立案が拒否したのは在庫更新条件の反転であり、拒否の根拠は固定モデルと対応する命令の差だった。最初の正常入力は各環境で約0.8〜1.0秒を要した。ランナーは別で、各１回なので速度による優劣は判定しない。 [比較実験のCIと成果物](https://github.com/s4na/keisiki/actions/runs/45567453725)

**対応範囲を明示した決定論的な生成を、業務ロジックの通常の検証経路にする。** 今回は同じ入力で意味上の反例を出せた範囲が広かった。確保判断・数量計算を扱う範囲から始め、生成器の構文追加には正常例、同値な書き換え、陽性対照、対象外、実行エラーの確認を含める。予約 INSERT のバインドやトランザクションの性質は、対応の言明を拡張した上で、まず実 Rails と PostgreSQL の履歴で照合する。 [実行履歴との統合 #23](https://github.com/s4na/keisiki/pull/23)

独立に書く Lean は、業務仕様と定理、または手動で扱うモデルの候補として使う。コードとの対応を主張する場合は、対象 Ruby を別の決定論的な経路で型付き表現に取り込み、Lean 上で対象モデルとの等しさか意味保存を検査する。構文上の等しさだけを使う場合は、受理する範囲を明記する。ソースの SHA-256 は入力の特定に使い、それぞれの意味上の根拠を証明または照合結果として記録する。

運用では、業務仕様と受け入れ例の担当、Ruby の取り込み・対応検査の担当、Lean の証明案を書く担当を分けられる。LLM やサブエージェントには必要な入力だけを渡し、証明型と公理を人が確認して CI で検査する。共通の判定入力は候補のコミットを固定してから実行し、修正が必要なら元の結果と修正後の結果を併記する。今回分けたのは候補の実装担当と比較入力で、長期の保守や複数の業務操作への展開は次の検証範囲になる。 [Lean の証明検査](https://lean-lang.org/doc/reference/latest/ValidatingProofs/)
