# Ruby の実行意味論と検証基盤

## 目的

Ruby ソースと、実装から独立した性質を入力にします。構文の取り込みと形式表現の生成は決定論的に実行します。アプリケーション実装を別の言語へ書き直す作業は不要です。証明の探索にどのツールを使っても、採用する証明の形と依存公理を Lean で検査します。

## 処理の流れ

1. Ruby 側で、指定ファイルを読み、そのバイト列の SHA-256 を記録して Prism で解析します。
2. 許可した構文だけを型付きの `Source.Expr` に取り込みます。定義一覧とソースのダイジェストを整列し、Lean のモジュールを生成します。呼び出し先の存在、引数の個数、呼び出しグラフが非循環であることをこの段階で検査します。
3. Lean で `Source.Expr` の評価を定義し、`lowerProgram` で IR に変換します。IR は演算と条件分岐を正規化します。たとえば `lhs > rhs` は、両辺の評価順序を保ったまま `lhs ≤ rhs` と分岐先の交換に変換します。
4. `lower_sound` と `lower_arguments_sound` が、任意の引数・呼び出し環境で各式と引数列の結果が保存されることを示します。`execute_lower` が、任意の呼び出し深さでメソッド解決、引数の評価、正常値・エラーが一致することを示します。プログラム全体の実行には `invoke_lower` を使います。
5. 利用者はメソッド名と事前・事後条件を `Contract` に書き、証明を渡します。`Holds` は事前条件を満たすすべての入力で、メソッドが値を返して事後条件を満たすことを要求します。正常な結果が１つも存在しない実行を成功扱いにしません。`RefutesAt` は具体的な入力で、事前条件を満たし、実際の形式評価結果が事後条件に違反することを要求します。

`Source.invoke` は、取り込んだメソッド数を同時にネストできる呼び出しの上限として使います。非循環の呼び出しグラフでは、同じメソッドが１つの呼び出しスタックに２回登場しません。この上限は整数の値や全称証明の入力範囲を制限しません。評価が上限に達した場合、形式上も `callBudget` エラーになります。

## 保証範囲と信頼するもの

| 区間 | 根拠 |
| --- | --- |
| Ruby バイト列 → Prism → Lean の `Source.Expr` | バージョンを固定した Prism と決定論的な取り込みの実装を信頼します。この区間の意味保存は未証明です。同じソースを CRuby と Lean で評価する差分テストを実施します。 |
| `Source.Expr` → IR | Lean で定義した `lowerProgram` と、カーネルが検査した `invoke_lower` が根拠です。 |
| IR・ソース意味論上の性質 | Lean カーネルが、指定した性質の証明を検査します。実行基盤が別モジュールで証明の型を照合し、`#print axioms` の結果を監査します。許容する公理は Lean 標準の `propext`、`Classical.choice`、`Quot.sound` です。 |
| 実行環境との対応 | CRuby 4.0、通常の `Integer` 演算、新規トップレベルモジュール、入力として渡したファイルで閉じた呼び出しグラフを前提とします。定数やメソッドの再定義、外部からの副作用、GC やリソース枯渇などは別の意味論が必要です。 |

現在のサブセットは、整数リテラル、必須位置引数、整数の加減算、`>` を条件とする `if/else`、括弧、トップレベルの名前付きモジュールに属する `def self.method`、明示レシーバーのメソッド呼び出しです。１つの呼び出しは複数ファイルをまたげます。各メソッドの本体は整数値を返す式１個です。未対応の式、未定義の呼び出し、再帰、引数の不一致は、変換の時点で報告します。

証明ファイルで `sorry` を使うとエラーになります。未承認の公理や `native_decide` 由来の公理に依存する証明は監査で拒否します。証明戦術の不成功は `UNKNOWN` であり、反例の証明や安全性の証明とは別の結果です。

## 拡張の順序

1. Prism AST から形式構文への取り込みを、検査可能な構文データと照合する。ソースごとに Ruby、Prism、依存関係のバージョンと入力ファイルのダイジェストを紐づけ、ruby/spec の対応項目を増やす。
2. 例外と可変状態を評価関係に加え、オブジェクトとメソッド表、クラス・継承・Mixin・動的ディスパッチを定義する。閉じた整数の証明はその部分言語として維持する。
3. ブロック、クロージャ、クラスの再オープン、メタプログラミング、`require`・`autoload` を順に扱う。Gemfile.lock と実際に読み込んだソースを記録し、依存の変更で関係する証明を再検査する。ライブラリの定理は同じ意味論の下で再利用する。
4. ネイティブ拡張やDB、OS、時刻などは明示的な外部契約で表し、対象実装がその契約を満たす根拠を管理する。Thread・Fiber のスケジューリングと共有状態の評価関係を定義する。
5. Rails の実ソースをアプリケーションや Gem と同じ入力として解析する。HTTP 全体の性質を扱う段階では、最初に検証するリクエスト経路と外部境界を定義し、未対応の処理が到達可能なら保証範囲に含めない。
