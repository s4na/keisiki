# 再送の有限モデル検査

TLA+ で #8 の P1（同じ確保要求の再送は一度だけ反映される）のうち、在庫２個・予約 ID １種・数量１個で、初回コミット後に応答が失われ、同じ要求を１回再送するケースを検査する。TLC は初期状態から到達可能な状態を幅優先で探索し、各状態で P1 を確認する。再送完了は意図した終了状態として扱う。

| TLA+ の遷移 | 共通課題で対応する観測 |
| --- | --- |
| Commit | 確保記録１件と在庫１個が同じトランザクションで確定する。初回の処理結果を保持する |
| LoseResponse | コミットと独立した応答喪失が起きる。確保記録と在庫は変わらない |
| Retry | 同じ予約 ID・数量の再送に、初回と同じ処理結果を返す。正常版の在庫は変わらない |

不具合版では Retry の在庫更新だけを変更し、再送で再度減算する。PR #16 の二重更新と同様に、初回コミットと確保記録１件は変わらないが、再送後の残在庫が０個になる。CI は正常版の探索が完了し P1 違反がないことと、不具合版の P1 違反が上の３遷移からなることを確認する。TLC の起動・設定エラーは不具合検出と区別してジョブを失敗させる。

TLC 1.8.0 の JAR と Java 21、jq がある環境で検査できる。

```sh
TLA2TOOLS_JAR=/path/to/tla2tools.jar bin/check-reservation-retry-model tmp/reservation-retry-model
```

出力先には TLC の各ログと、機械可読な `counterexample.json` および結果の `result.json` を保存する。保証範囲はこの TLA+ モデルの有限状態で、トランザクションの原子性、HTTP/SQL の引数、並行実行はモデル内の処理に抽象化した。#10 の採用契約との対応と、#12 の制御点を使った Rails/PostgreSQL 上の反例再生は、各基盤が揃ってから接続する。
