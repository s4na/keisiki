# コミット後の再送を Lean・TLC・実行履歴で照合する

Rails と実 PostgreSQL の [PR #16](https://github.com/s4na/keisiki/pull/16) と、TLA+ モデルの [PR #21](https://github.com/s4na/keisiki/pull/21) を同じ変更に取り込む。在庫２個、予約 ID １種、数量１個、コミット後の応答喪失と同一要求の再送１回を３方式で扱う。

| ジョブ | 証拠 |
| --- | --- |
| `app-smoke` | 実 HTTP と PostgreSQL 18.6 を実行する。初期状態、初回コミット、応答喪失の観測直後、再送後の確定行を別接続で読む。対象の書き込み SQL、型変換されたバインド値、接続、更新件数、コミットを記録する。 |
| `model-check` | TLC が正常モデルの全４状態で P1 を確認し、二重更新モデルから３遷移の反例を出力する。 |
| `retry-conformance` | Lean 4 が純粋な遷移の定理を検査する。正常版の４状態を Lean と実機で照合する。二重更新版は TLC の反例も含む３方式で在庫・確保記録・処理結果を照合する。順序、SQL、バインド値が違う場合や記録が欠ける場合には失敗する。 |

Lean の正常版の定理は、在庫が要求数以上で要求数が正なら、抽象化した確保で１件記録し、応答喪失と同一要求の再送の間に別の更新がなければ、在庫を維持して同じ結果を返すことを示す。二重更新の定理は今回の具体値で残在庫が０になることを示す。Rails の書き込み履歴は今回観測した実行との対応を裏づける。Rails 全体、他の操作が介在する場合、PostgreSQL 本体の正しさは別の主張になる。

CI 成果物 `reservation-retry-conformance` に Lean が計算した JSON、定理の依存公理、照合結果を保存する。元の SQL 履歴と TLC の反例は各入力ジョブの成果物に残る。
